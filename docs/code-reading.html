Drone Lab 源码阅读路线

先理解“谁产生数据、谁做决策、谁执行动作”，再读数学公式。文件头解释模块职责，函数前解释契约，函数内部解释关键步骤。C/C++ 的 @brief 是摘要，@param 是参数，@return 是返回值，@note 是调用条件。

1. 三条链路分别读

链路数据流源码
实物采集飞控串口、Nano 上两颗 ToF → JSON → 热力图和录制文件app/main.py → workers.py → nano/main.c → platform.c
离线预研输入数学参数 → 一次模型计算 → 图表和结果文件research_panel.py → research/runner.py → 各研究模型
物理飞行物理世界生成观测 → 定位 → 飞控 → 新的物理状态launch_linux.py → runner.cpp → estimator.cpp

采集链管理 I²C 和串口；仿真链生成三颗 ToF、光流速度、UWB 等观测。两者即使都输出 JSON，也需要按字段和时间基准适配。板端采集程序不是整套自主飞行程序。

2. 点击启动后发生什么

app/main.py：创建实验台窗口
  └─ app/simulation_panel.py：响应“启动多机环境”按钮
       └─ simulation/launch_linux.py：通过 WSL 准备地图并启动进程
            ├─ Gazebo：物理模型、碰撞和传感器
            ├─ PX4 × N：速度/姿态闭环、电机输出
            ├─ drone_companion_runner × N：每机独立定位和控制参考
            ├─ team_coordinator：全队阶段与目标点
            └─ evaluate_linux.py：独立记录真实位置与物理接触

进程就是独立运行的程序。一架飞机对应一个 PX4 和一个伴随程序。Qt 的 QProcess 用于启动程序，QTimer 用于定时刷新界面，Signal/信号用于把后台结果通知主界面；槽函数是收到信号后执行的函数。

地图 JSON 定义 spawns 起飞点、team_mission 任务和 uwb_anchors 基站；simulation/config.json 定义伴随参数。每次启动会复制配置到独立运行目录，分析某次结果要读那次快照。

3. 从传感器到控制的完整数据流

Gazebo 深度/相机 → sensor_gateway.cc → ToF JSON / 相机文件
Gazebo peer_height_system.cc → 高度 / 光流速度 / UWB JSON
                                 ↓
runner.cpp → protocol.cpp 解码 → Estimator 融合
                                 ↓
             Estimate：位置、速度、协方差、有效性
                ├─ 广播给邻机，支撑 UWB 协同定位
                ├─ 上报 team_coordinator
                └─ ODOMETRY 发给 PX4
team_coordinator → TeamMission::step → 每机目标点
runner：目标误差与速度阻尼 → 速度/姿态参考 → PX4 → 电机 → Gazebo
通道回环 UDP 端口含义
传感器16000 + 机号观测值，不是完整的位置答案
邻机估计17000 + 机号位置、方差、参考来源和传播路径

队伍状态18100各伴随程序汇总状态

UDP 逐包传输；MAVLink 是飞控消息协议，带消息类型、字段和校验，一包 UDP 可能含多个 MAVLink 消息，所以 runner 按字节送入解析器。JSONL 是“一行一个 JSON”，适合边写边读和回放。

4. 定位算法怎样读

先读 types.hpp 和 estimator.hpp，再按下面顺序阅读实现。

步骤函数直观含义
初始化reset用已知起点建立共同坐标系。七维状态顺序为 x、y、z、yaw、vx、vy、vz。
运动预测advanceTo / predict根据经过时间、速度和可用加速度推算新状态；不确定度随预测累积。
光流fuseOpticalFlow接收成品模块给出的机体系水平速度，结合姿态与世界系速度比较。
ToFfuseTof把深度与静态地图匹配，利用可信结构修正漂移；平坦地面不能提供完整 XY 约束。
机间 UWBfuseUwb距离、方位与邻机估计共同约束本机；参考序号和路径防止重复利用同一依据。
基站fuseAnchorRange已知基站坐标约束测距方向；完整 XY 参考还需近期有效测距的方向足够独立。
统一更新update比较预测与实际观测，按不确定度分配修正量。

协方差 P表示状态有多不确定，以及不同误差是否相关。对角线是方差，非对角线描述相关性。残差是观测与预测的差，雅可比 H表示状态变化对观测的影响，卡尔曼增益 K决定修正多少，随状态方差和测量噪声变化。

可观测性回答“测量能否区分某种移动”：沿无限长墙平移，墙距可能不变，因此沿墙方向缺少定位依据。ToF 信息矩阵的特征值用来找有信息的方向；不能把缺少观测当作误差已消失。

5. 坐标系与时钟

名称含义用途
世界 ENUX 东、Y 北、Z 上；场地采用共同世界坐标地图、估计位置、任务目标
机体 FLU前、左、上光流速度、安装关系、内部参考
机体 FRD前、右、下；FLU 转换时 Y/Z 反号飞控接口
姿态角源码主要用 rad，界面可转 °；yaw 偏航、roll 横滚、pitch 俯仰坐标旋转和控制
sim_time_us共同仿真时刻，μs预测、测量年龄、阶段计时
现实单调时间不随系统日期调整倒退收包超时、刷新、播放节拍

两种时钟不能直接相减。计算机算得慢会使现实等待更长，不能因此改变物理时间戳。高度 0.75 m 是世界高度，平台 z=0.5 m 时只高出平台 0.25 m。

6. 谁决定下一架起飞或撞击

读 team_mission.hpp 类型，再读 TeamMission::step。

WAIT_READY 就绪 → TAKEOFF 起飞 → TRANSIT 航路 → ASSEMBLE 集结
→ [APPROACH 接近 → CONTACT 接触 → RETREAT 退出] 按 order 循环
→ RETURN_ALL 返航 → LAND_ALL 降落 → COMPLETE 完成

phase_ 是全队阶段，turn_ 是顺序表下标，order[turn_] 才是机号。barrier 是同步条件，要求条件持续成立，防止掠过目标被当作停稳。degraded 是单机当前不可用，skipped_ 保存未完成轮次的记录；恢复通信不等于补做历史轮次。

runner 使用 v_ref = Kp × 位置误差 − Kd × 当前速度：前项拉向目标，后项抑制过冲。PX4 再把速度误差变成姿态和电机指令，所以伴随位置控制与飞控闭环是两层控制。接触冲击由传感器判断，物理接触日志由评估器另行核验。

7. 从现象找到源码

现象先看记录再看代码
不进下一阶段team_status.json 的 phase、degraded_reason、skippedvalidForBarrier、step
定位误差变大estimate、fusion.reason、参考路径fuseTof、fuseUwb、estimate

过冲或撞后不退出任务参数、control_intention、IMU 冲击runner 的控制生成与姿态恢复

ESTIMATE 是算法估计，真实位置只用于评估。flight_data.py 在短间隔内插值对齐图表，localization_metrics.py 使用自己的匹配统计口径，比较时要检查时间容差与取样方式。

8. 建议的第一次阅读

  1. 先运行任务并打开曲线，看阶段与轨迹怎样对应。
  2. 读 main.py 创建窗口，再读 simulation_panel.py 的 command，找到按钮怎样启动 WSL。
  3. 读 launch_linux.py 的进程、端口和配置快照，再沿 runner 的编号主循环阅读。
  4. 读 types.hpp 与 estimator.hpp 的输入输出，逐个进入融合函数。
  5. 读 team_mission.hpp/cpp，跟踪单机接近、接触、退出和全队返航。
  6. 最后读 Gazebo 插件、地图射线、板端采集和研究模型，理解数据如何产生。

修改速度看地图 team_mission；修改定位噪声看 EstimatorConfig 及实际配置加载路径；改显示看 app；改真实驱动看 nano。test_flow_cooperation.cpp 演示共享参考，test_variable_team.cpp 演示可变机群，tests/test_flight_data.py 演示时间对齐。

生成模型应改 generate_sensor_models.py，场地应改地图配置。vendor、生成目录、构建缓存和历史日志不是手工修改入口。JSON 不支持注释，参数说明见源码和接口说明。
