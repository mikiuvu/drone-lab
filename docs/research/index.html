RV Nano 同时做视觉和定位：现在能确定什么

日期：2026-10-02。对象：DM-FC01 + LicheeRV Nano / SG2002 + 两颗 VL53L5CX，后续增加相机与可选 UWB。研究采用电脑仿真与实现分析；硬件性能待板上测量。

结论：Nano 是否够用，不能由 1 TOPS 或电脑运行速度判定。当前更值得推进的基线是单 Linux CPU 预算、低频检测与必要的 ROI 跟踪、NPU独立推理、固定频率的小规模定位任务、有界最新帧槽，以及独立的状态新鲜度检查。最大风险同时来自视觉链路适配、应用可用内存、观测覆盖和时序，不只是数学计算量。

三个需要先调整的方案假设

  1. 当前没有已证实的连续里程计。飞控 IMU 和两颗水平 ToF 不自动构成全场可靠 x/y/yaw。原方案的光流+下视测距被暂时移除后，需要补回这个角色，或者证明结构观测与有界预测在所有任务航段足够。
  2. 标称 256 MB 不是全部可用堆内存。官方在线配置存在较大的 ION/多媒体保留区。具体镜像的内存分区、VB池和模型工作区必须在后续板端测量；主核与辅助核也不能默认等同两个可用 Linux CPU 核。
  3. 实时性看结果年龄和尾延迟。低 CPU 百分比也可能伴随严重视觉积压。为避免旧目标继续影响导航，帧序号、源时间戳、epoch、队列上限和过期丢弃是代码接口的一部分。

如何在图形界面复现

  1. 重新打开桌面“Drone Lab 实验台”，选择“⑥ 预研与仿真”。
  2. 选择“任务调度与图像排队”，先默认运行，再将 NPU 服务时间改为60 ms、CPU预处理6 ms、后处理4 ms，重跑比较。
  3. 选择“双 ToF 几何与可观测性”，先保持高度2.5 m、量程3 m、安装俯仰0°，再改为−30°。正角朝上，负角朝下。
  4. 选择“时间错配与接口门控”，把错配从50 ms改成10 ms，查看误差变化。
  5. 每次结果保存到 research/results，含输入配置、UTC时间、模型源码SHA256以及指标；PNG可单独分享。模型迭代后应重新生成证据，不能只保留旧截图。

实现路径与取舍

路径采用条件提前处理的成本
当前 Nano + 轻量定位 + NPU检测实际完整视觉链路帧龄/内存/温度达到任务要求，航路观测可靠相机SDK、算子量化、内存所有权、CPU后处理、采样对时、检测/跟踪分频。建议作为首个可测基线。
阶段性调度：巡航定位为主，近目标视觉为主各阶段都保持独立的基本运动状态与失效出口切换必须有条件和滞回；不能为省算力关闭避障/状态有效性检查。模型热切换可能导致内存峰值和长暂停。
额外轻量实时节点/辅助核有可验证的SDK、时钟和接口可卸载采集/时间戳/看门狗，不自动解决 Linux 视觉处理；增加通信、供电、重量和调试成本。
更强伴随计算板真实模型转换失败、无法满足帧龄/内存/驱动要求，优化后仍失败按完整链路做同输入AB测试；同时核对重量-尺寸、电源瞬态、散热。不能只按TOPS排位采购。
地面/机库计算只有正式规则、链路延迟及失联处理都允许才考虑当前未确认飞行中持续通信权限；不作为基础姿态/状态估计唯一依赖。
