LicheeRV Nano 算力评估

硬件与当前算法

Sipeed 官方规格：SG2002，主核 1 GHz RISC-V C906 / ARM A53 二选一，辅核 700 MHz C906，256 MB DDR3，NPU 1 TOPS INT8 / 支持 BF16。Linux 可用核数、频率和可用内存须以实际系统为准，不把辅核自动当作第二个 Linux 工作核。

当前灯条检测、OpenCV PnP、Eigen 定位/跟踪均为 CPU 算法，未调用 NPU。1 TOPS 不能替代 CPU 预算。每架 Nano 只承担本机图像和定位，加邻机消息；四机桌面仿真负载不能整体压到一块 Nano 上。

推荐实施顺序

  1. 按相机图像、ToF结构密集/退化区、邻机数分别测 C++ 实代码；报告 p50/p95/p99、CPU时间、峰值内存和帧龄。
  2. 用已有“⑥ 预研与仿真”的调度模型输入各阶段耗时；扫描 5×、10×、20×等独立倍率，比较最新帧策略、降分辨率、减少地图匹配频率。
  3. Gazebo 里注入完成时延、抖动和丢帧，保留原曝光时间戳；延迟施加在处理任务上，不能全局减慢仿真时钟冒充算力不足。
  4. 有板后交叉编译同一基准，启用板端 OpenCV。用 scripts/profile_nano.py 与实际相机/ToF/UWB 并发采样 /proc、温度和频率；以实测校准每个阶段倍率。
  5. 测试热稳态至少10分钟，并覆盖曝光变化、满图噪声、失锁重识别、地图匹配最坏区域和无线突发。检查控制更新是否过期，而不只看平均 FPS。

建议预算目标：持续 CPU 工作量不超过单核约70%，控制周期20 ms和相机周期分别核验；这是设计余量，不是厂商保证。结论：当前不能证明板端算力充足，但已具备实代码基准和预算模型，能先排除明显超载方案。
